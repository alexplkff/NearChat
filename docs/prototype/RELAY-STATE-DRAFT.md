# Передача сообщения: черновик состояний

Статус: техническое предложение для обсуждения. Принятые требования остаются в [Требованиях NearChat](../requirements/REQUIREMENTS.md); этот черновик не подтверждает реализацию или испытания.

Рассматривается одна ветка и один конечный адресат. Для группы нужны отдельные задачи адресатов; первая галочка в интерфейсе не завершает остальные задачи. По REQ-103 в интерфейсе остаются только галочки по первому получателю, без подписи с числом подтверждений.

## Состояние задачи и известный результат

| Событие | Копия и ответственность | Известный отправителю результат |
| --- | --- | --- |
| Исходящая задача создана, пути нет | Собственные данные в бюджете истории | «Ожидает маршрута» |
| Попытка передана дальше без квитанции | Факт отправки не разрешает удалить ответственную копию | «Ожидает подтверждения» (REQ-101) |
| Промежуточное устройство пересылает без записи | Надёжная ответственность не передана; предыдущая копия сохраняется | Галочки нет |
| Следующий узел сохранил задачу и вернул достоверную квитанцию | Прежний ретранслятор освобождает свою копию/задачу; у исходного отправителя остаются запись и ожидание по REQ-068 | «Передано ретранслятору», галочки нет |
| Конечный адресат принял сообщение, квитанция дошла | Соответствующие задачи доставки завершаются | ✓ «Доставлено», включая приём адресатом только в RAM |
| Получена квитанция прочтения | Подтверждён показ на экране по REQ-059 | ✓✓ «Прочитано» |
| Срок истёк без конечной квитанции | Локальная задача прекращается; собственная история остаётся под FIFO | «Доставка не подтверждена», «Повтор» / «Отмена» |

Это локальные знания и задачи, а не глобальный перечень копий. Во время потерянного ответа оба соседних устройства могут сохранять данные. Глобальное число копий по-прежнему отложено.

## Получатели группы

По REQ-104 набор фиксируется из последнего достоверно известного отправителю состава при отправке. Позднее присоединение не расширяет его задним числом. Известные запреты после выхода, исключения или завершения всё равно применяются; фиксированный набор адресатов не означает безусловное право продолжать каждую задачу до срока. По REQ-105 пользовательский «Повтор» создаёт новый набор по известному составу в момент новой отправки, включая уже известных новичков. Автоматический повтор прежней передачи исходный набор не меняет. Для технической модели нужно различать историю адресации, состояние задачи и период членства получателя, а не определять их только по часам.

## Инварианты предлагаемой технической модели

1. Квитанция надёжного приёма создаётся после фиксации конверта, задачи и необходимого состояния дедупликации. Ошибка записи не превращается в успех. Конкретный механизм атомарности ещё не выбран.
2. Отсутствие квитанции запускает повтор той же передачи по REQ-079, с прежним идентификатором и сроком. Повтор не создаёт новую запись и не восстанавливает удалённый FIFO текст.
3. Дубликат не означает автоматическое повторение успешной квитанции. Нужно различать действующую задачу, передачу ответственности дальше, конечную доставку и досрочный отказ. Привязка и порядок таких доказательств пока требуют проработки.
4. При разрыве немедленного транзита нет новой надёжной задачи на транзитном устройстве; прежняя ответственная задача сохраняется в пределах исходных условий.
5. Состояния доставки и прочтения применяются монотонно: достоверная квитанция прочтения уже подразумевает конечный приём, а поздняя квитанция только доставки не понижает ✓✓ до ✓. Удалённая история не восстанавливается.
6. Сообщение, пользовательская «Повторная отправка» и автоматический повтор передачи различаются. Только пользовательский «Повтор» создаёт новое логическое сообщение и срок.
7. Галочка сообщения не меняет членство группы и не активирует завершённую группу или отменённое вступление.

## Порядок истории

REQ-102 задаёт локальный порядок добавления: входящие в конец при получении, исходящие при локальной отправке. Этот порядок сохраняется после перезапуска и не пересчитывается по часам отправителя. Он отделён от времени создания для срока жизни, версий членства и состояния квитанций. Дубликат не получает новую позицию в истории.

## Контрольные случаи для дальнейшего разбора

- Запись на промежуточном устройстве не удалась, но немедленный транзит успешен: копия у ответственного узла сохраняется до надлежащей квитанции.
- Задача сохранена следующим узлом, ответ потерялся: прежний узел не удаляет копию по предположению; повтор обрабатывается идемпотентно.
- Чтение подтверждено раньше, чем дошла отдельная квитанция доставки: сразу ✓✓, последующий ответ не понижает статус.
- Принявший ответственность пользователь подтвердил уменьшение буфера: это разрешённый досрочный отказ с возможным прерыванием доставки, а не гарантия сохранности последней копии.
- Копия исчерпала 256 переходов до адресата: прекращается эта ветка без уведомления по REQ-080. Доставку на допустимом 256-м переходе принимать.

Сценарии здесь описаны, не исполнены. Пример отмены вступления отдельно доступен в [интерактивном макете](group-join-race.prototype.html).

## Что ещё открыто

Нужны формат и подлинность квитанций, привязка к адресату/попытке/периоду членства, актуальность уведомлений, схемы атомарной записи и восстановления, ограниченные служебные отметки, учёт RAM транзита, параметры повторов и корректная реализация бюджета пути. Угроза нечестных устройств рассматривается в билете безопасности; количественные пределы требуют отдельной проработки нагрузки.

Дополнительный статус «Ожидает подтверждения» принят пользователем в REQ-101; это не подтверждение всей технической модели. Он покрывает промежуток после отправленной попытки, когда нет подтверждения ответственности ретранслятора или конечного приёма; это уточнение открытого вопроса прямой передачи, а не галочка доставки.
